QML Dimension Problem — Root Cause Analysis

ADMET benchmark · admet branch · July 2026

Executive Summary

Every quantum model crash in the pipeline traces to a single architectural mismatch: the pipeline sends raw molecular fingerprints (up to 2,048 features) directly to quantum algorithms that require one qubit per feature. A classical statevector simulator needs a 2N-element complex array to represent N qubits. For N = 2,048, that is a number with ~600 decimal digits — not just too large for RAM, but too large for any integer type that can describe an array length. The crash is therefore not a bug to be patched around; it is a hard mathematical impossibility that requires a design decision about the qubit budget.

Additionally, MMELON fails for a completely different reason: the installed version of transformers (4.50.3) does not register ibm-research/biomed.sm.mv-te-84m as a known model type because the model uses custom code not bundled with that release.

How Features Flow Into Quantum Models

qprofiler.py loops over two embedding passes controlled by embeddings: ['none', 'pca'] in admet_config.yaml. On each pass it calls model_run(), which runs all models — classical and quantum — in a single Parallel pool: 

for embed in ['none', 'pca']:                          # line 160
    X_train_emb, X_test_emb = get_embeddings(embed, X_train, X_test, n_components=10)
    model_run(X_train_emb, X_test_emb, y_train, y_test, data_key, args)
    # → Parallel([compute_svc, compute_rf, ..., compute_qnn, compute_vqc, compute_pqk, ...])

On the 'none' pass, X_train_emb is the raw scaled fingerprint — 2,048 columns for ECFP4, 167 for MACCS, 200 for RDKit200. Every quantum model receives this directly. On the 'pca' pass it is reduced to n_components=10, which works for QNN/VQC/QSVC/PQK (10 qubits each), but QEnsemble still fails at 27 qubits.

Exact Qubit Requirements Per Model and Featurizer

QNN / VQC / QSVC / PQK — one qubit per input feature

All four use get_feature_map(feat_dimension=X_train.shape[1]), which creates a ZZFeatureMap with exactly feat_dimension qubits. The statevector simulator allocates a complex128 array of length 2feat_dimension.

The Qiskit Statevector Simulator Limit

The simulator is StatevectorEstimator (Qiskit's statevector primitive). It allocates a numpy complex128 array of shape (2**N,). The actual failure modes are:

  • N ≤ 30: Works fine (<16 GB for the statevector)
  • N = 32–35: Possible on high-RAM nodes (68–512 GB), but prohibitively slow
  • N = 36: Fails with MemoryError: Unable to allocate 1.00 TiB — confirmed on the cluster nodes
  • N ≥ 37: Same memory error — numpy cannot allocate the array
  • N ≥ 64 (e.g. 167, 200, 2048): The ValueError: Maximum allowed dimension exceeded error — this is not a memory error; it is numpy's own overflow check when 2**N exceeds the platform's intp max (263 on 64-bit). numpy refuses to even describe the shape.
Key insight: For ECFP4/MACCS/RDKit200 with embed='none', the crash happens before any circuit runs — during feature map construction in get_feature_map() or during the first neural_network.forward() probe call. The error is a numpy array shape overflow, not an out-of-memory error. No amount of additional RAM would fix it.

MMELON — A Separate Issue

ibm-research/biomed.sm.mv-te-84m is an IBM Research model that uses a custom model architecture registered via the HuggingFace trust_remote_code mechanism. transformers 4.50.3 raises ValueError: Unrecognized model even with trust_remote_code=True because the remote code itself fails to load (likely a network issue on cluster nodes or a missing model_type field in the config.json that the remote code depends on). This is independent of the qubit problem.

Confirmed via direct test: AutoConfig.from_pretrained("ibm-research/biomed.sm.mv-te-84m", trust_remote_code=True) still raises the same ValueError on the cluster. The model either requires internet access to fetch remote code (blocked on compute nodes) or a newer version of transformers with first-class support.

Design Options for the Scientific Article

There are three architecturally sound paths, not mutually exclusive:

Option A — PCA gate (already in the config, just needs enforcement)

The config already has embeddings: ['none', 'pca'] and n_components: 10. The intent is clear: QML models should only run on the PCA-reduced data. The architectural fix is to skip quantum models on the 'none' pass inside model_run.py. Classical models run on raw features; quantum models run only on PCA-10. 

quantum_models = {"qsvc", "qnn", "vqc", "pqk", "qensemble", "mmelon"}

# In model_run(), when building the delayed() list, check the embedding:
if method in quantum_models and X_train.shape[1] > MAX_QUBITS:
    # skip — return NaN row directly, do not even schedule
    continue

This is already the scientific intent: compare classical fingerprint-based models vs. QML on PCA-compressed representations. This is the recommended fix. It requires changing one place (model_run.py) and adding a config key for max_qubits (e.g. 26).

Option B — Featurizer-aware qubit budget

Introduce a train_qml.csv split (already produced by the data prep script — it has the same 2,048 columns but a smaller sample count). Reduce QML features at preparation time using VarianceThreshold + PCA to exactly n_components, write a separate train_qml_pca.csv, and only point QML models there. This decouples QML feature engineering from the classical feature pipeline.

Option C — Subspace feature maps (most scientifically interesting)

For the paper, you could implement random feature subsampling: draw n_components features uniformly at random from the full fingerprint, repeat with multiple seeds, and average. This preserves the connection to the original chemical representation rather than projecting into PCA space. It is a legitimate QML design choice documented in the quantum kernel literature.

QEnsemble power-of-2 padding (separate fix needed regardless)

Even with PCA-10, QEnsemble's normalize_data does not pad to the next power of 2. The prepare_training_set function should pad each sample to length 2⌈log₂(n)⌉ before returning. Without this, QEnsemble fails for any n_components that is not itself a power of 2. 

# Fix in data_encoding.py → prepare_training_set():
import math
def normalize_data_padded(x):
    n_pad = 2 ** math.ceil(math.log2(len(x))) if len(x) > 1 else 2
    padded = np.zeros(n_pad)
    padded[:len(x)] = x
    norm = np.linalg.norm(padded)
    return (padded / norm).tolist()       # returns length = power of 2

With PCA-10: n_pad=16, qubits_per=4, total qubits = 7 + 5×4 = 27. Marginal for the statevector simulator (~8 GB for 227 elements), but feasible. Reduce to n_components=8 → 23 qubits → 1 GB → comfortable.

MMELON (separate from QML)

Two paths:

  1. Upgrade transformers: uv pip install "transformers>=4.52" — check if newer versions natively support this model type.
  2. Use a local model snapshot: git lfs clone https://huggingface.co/ibm-research/biomed.sm.mv-te-84m into the repo, point model_name at the local path. Solves the network access issue on compute nodes.

Recommended Immediate Action (Minimal Change)

One-line config change + one guard in model_run.py resolves all QML failures for the benchmark:
  1. In admet_config.yaml: set n_components: 8 (power of 2, 23 qubits for QEnsemble, safe for statevector)
  2. In model_run.py: add a guard — if X_train.shape[1] > n_components and method in quantum_models, return a NaN row without spawning the subprocess. This prevents the 'none' pass from ever dispatching QML.
  3. In data_encoding.py → normalize_data: pad to next power of 2 for QEnsemble compatibility.
  4. For MMELON: test pip install --upgrade transformers or use a local model path.

This approach is scientifically clean: it makes the paper's experimental design explicit — "quantum models operate on PCA-8 representations of molecular fingerprints; classical models operate on the full fingerprint" — which is standard practice in near-term QML benchmarks and aligns with the qubit budget of current quantum hardware (typically 27–127 qubits on IBM devices).
